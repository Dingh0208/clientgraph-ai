## 1. 从明确的下一步动作生成

输入是带动作线索的来源文本（聊天、通话、邮件、文档），生成：

| 字段 | 规则 |
|---|---|
| 事项 | 动作句子，最长 80 字 |
| 负责人 | “负责人：X”“由 X 负责”“王工，请…”；没有则留空并生成待确认 |
| 客户 / 项目 | 来自证据归属或导入上下文 |
| 截止时间 | **只写完整年月日**；`下周/尽快/月底` 不写值 |
| 来源 | 文件、来源类型、locator、原文、发生时间 |
| 优先级 | 紧急/今天/已逾期 → P0；重要/本周 → P1；其余 P2 |
| 状态 | open / done；延期只改截止时间，不新增状态 |
| 风险 | high / medium / low + 说明（逾期、今天到期、3 天内、常规） |

模糊日期生成 `due_vague` 待确认问题；无日期生成 `due_missing`；无负责人生成 `owner_missing`。

## 2. 操作

| 操作 | 规则 |
|---|---|
| 完成 | 仅 open → done，记录完成时间、操作人、历史 |
| 延期 | 仅 open，必须提供明确的年-月-日；记录前后截止时间、延期次数、原因 |
| 重新打开 | 仅 done → open，清空完成时间，记录原因 |
| 批量 | 完成/延期/重新打开按 ID 逐条执行；失败的条目返回错误码，不阻塞其他条目 |

每次操作写入 `history`：动作、时间、操作人、前后值、原因。

## 3. 提醒策略

### 3.1 候选

- 到期待办：`due_at <= 今天` 且状态 open；逾期显示天数；
- 客户无跟进：最后联系超过 7 天（含从未记录）；
- 模糊/无截止时间的待办不进入到期提醒。

### 3.2 本地 Windows 通知规则

- 只有应用运行中才发送（`app_active=true`）；
- 22:00–08:00 为免打扰，不发送系统通知；
- 每个任务/客户每天最多一次；
- 通知器失败不写“已发送”，下一轮可重试；
- **应用退出期间不发送、不伪造已发送记录**；下次启动只返回应用内补看（`delivery=in_app`，`sent_at=null`）。

发送器为接口；测试使用 `FakeNotifier`。真实 Windows Toast 需要桌面端接入同一接口，策略层已按上述规则实现。

## 5. 限制

- 截止时间只接受完整年月日；`下周五` 等相对日期不计算。
- 负责人只识别显式写法，不按项目默认负责人推断。
- 平台通知为策略与接口层，测试使用 FakeNotifier；真实 Windows Toast 需桌面端接入。
- 客户无跟进的阈值固定 7 天，未按客户等级区分。
- 批量为逐条执行，不开事务；部分失败如实返回。
- 任务中心为内存实现，未接 SQLite/待办页面；原型 `NEXT_ACTIONS` 仍是静态展示。
- 风险等级由优先级与截止时间推导，不是模型判断。
- 未实现重复待办合并与跨项目去重。
