## 1. 输入与输出

输入是证据归一化后的条目（`clientgraph.evidence.v1` 的 `items`），每条至少包含：

- `text`、`source_type`、`source_file`、`occurred_at`
- `sources[].locator` 与 `sources[].meta`（发送者/收件人）
- 可选 `proposer`

输出：

```json
{
  "project": {
    "id": "p1",
    "name": "设备巡检小程序（一期）",
    "stage": {"value": "已签约", "evidence": {}},
    "budget": {"status": "conflict", "values": []},
    "acceptance_criteria": [],
    "evidence_count": 13
  },
  "requirements": [
    {
      "id": "R7",
      "title": "设备台账",
      "canonical_key": "设备台账",
```

## 2. 字段规则

| 字段 | 规则 |
|---|---|
| 项目 | 取上下文 `project_id/project_name`；未提供时用条目 project 候选 |
| 项目阶段 | 按关键词与最近时间：合同/签约→已签约；上线/实施→交付中；报价/方案→报价中；需求/评审→需求中；预研→线索 |
| 需求 | 含“需要/要求/必须/希望/要能/支持/增加/上线/审批/台账/巡检/统计/看板/二维码/异常/上报”等线索的句子 |
| 提出人 | 条目 `proposer` → 证据 meta.sender / email from；ASR 无说话人分离时为未知 |
| 负责人 | 仅从“负责人：X”“由 X 负责”提取；没有就留空并生成待确认 |
| 截止时间 | 只接受完整年月日（如 `2026-11-15`）或用户确认日期；`尽快/下周/月底/下个月` 不写值 |
| 预算 | `预算/报价/总价/合同金额 + 数字 + 万/元`；多值→冲突 |
| 验收标准 | 含“验收”或“以…为准”的句子，取冒号后的可验证条件 |
| 待确认项 | 模糊日期、缺失负责人、预算冲突/缺失、验收缺失、阶段未知 |

## 3. 截止时间：绝不猜日期

| 资料表达 | 处理 |
|---|---|
| `2026-11-15` | `status=explicit`，写入 `value` |
| 用户确认 `2026-11-12` | `status=user_confirmed`，写入 `value` |
| `10 月底` | `value=null`，`status=pending_vague`，生成“10 月底具体指哪一天”问题 |
| `下周` | `value=null`，生成“下周具体指哪一天”问题 |
| 同时出现 `10 月底` 与 `2026-11-15` | 写入明确日期，同时生成 `deadline_mismatch` 问题 |
| 无日期 | `status=missing`，不写值 |

## 4. 重复需求合并

- 用关键词归一为 `canonical_key`：设备台账、巡检计划、扫码巡检、统计看板、审批流、异常上报、上线时间、售后工单；
- 同一 `canonical_key` 的句子合并为一条需求；
- 保留全部证据（文件、locator、时间、原文），`merged_count` 为去重后的来源数；
- 不同项目不合并（按项目分组）。

验证：`设备台账` 由 2 条聊天 + 1 份需求文档 + 1 封邮件合并为 1 条，保留 4 个来源；`统计看板`、`审批流`、`上线时间` 各保留 2 个来源。

## 6. 限制

- 规则抽取，不做语义改写理解；同义但无关键词的表述可能漏抽。
- `canonical_key` 为固定关键词表，新业务词需要补充。
- 负责人只识别显式“负责人/由…负责”，不根据角色推断。
- 预算只识别常见格式；多币种、分期、税率未建模。
- 阶段是关键词+时间推断，不是流程引擎。
- 截止日期只接受完整年月日；`10 月 8 日` 缺年份时会进入待确认（未实现年份推断）。
- 提出人依赖证据 meta；ASR 未做说话人分离，通话提出人可能为空。
- 重复合并按关键词，不按语义相似度；不同项目的相同需求不会合并。
- 用户确认日期通过输入 `confirmed_dates` 传入，原型暂无确认 UI。
