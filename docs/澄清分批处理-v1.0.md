# 澄清分批处理 v1.0

> 日期：2026-11-06
> 状态：分批、取消、失败重试、追加资料实现并验证（27 项检查通过）
> 代码：`clarification/`、`scripts/verify_clarification_batching.py`
> 证据：`evidence/clarification-batching-2026-11-06.json`

## 1. 分批

- 按 `max_input_chars` 对选中资料分批；
- 单份资料超过上限时按段落/字符切分，保留 material ID、part 序号和 locator；
- 批次只装可读资料；不可读资料直接拒绝（`E_UNREADABLE`）；
- 每批记录 `batch_id`、输入字符数、material_ids、parts、状态、尝试次数。

示例：M01 1200 字、M02 1000 字、M03 900 字，上限 2000：

| 批次 | 字符 | 资料 |
|---|---|---|
| B1 | 1200 | M01 |
| B2 | 1900 | M02、M03 |

## 2. 进度与取消

- `progress()` 返回 `{completed, total, status, text}`，如 `1/2`；
- `process_next()` 处理一批，`process_all()` 顺序处理；
- `cancel()` 把未开始批次标记 cancelled，已完成批次、问题、证据、回答全部保留；
- 取消后不删除已完成的 Q/证据/answer。

## 3. 失败与重试

- 模型异常记录到批次 `error`（错误码 + 原因）和 `run.errors`；
- 失败批次之后保持 pending，已完成批次不重跑；
- `retry_remaining()` 只把 failed 批次改回 pending，沿用同一 `model` 和原资料；
- 完成批次的 question ID、证据、回答不变。

## 4. 追加资料

- `append_materials(new)` 只对新增资料做 plan；
- 新批次从现有批次号继续，旧批次不改；
- 新问题按 `key`/归一化文本与旧问题去重；
- 证据合并，`merged_count` 增加，不重复创建问题；
- 新旧值冲突时生成 `CF*` 冲突记录，保留旧值/旧回答，`overwrite=false`，状态 `conflict` 或 `must_confirm`。

## 5. 验证结果

| 场景 | 实际结果 |
|---|---|
| 两批计划 | B1 1200 字/M01；B2 1900 字/M02+M03 |
| 单资料超限 | 4500 字 → 3 批，每批 ≤2000 |
| 不可读 | `E_UNREADABLE` |
| 完整运行 | 2/2，2 个问题，1 个冲突（旧值 8 万保留） |
| 取消 | 1/2，B2 cancelled；Q1 回答“预算 8 万已确认”保留 |
| 失败 | 第 2 批 `E_MODEL_TIMEOUT`，完成 1/2 |
| 重试 | 2/2；第一批 question ID 不变；模型不变 |
| 追加 M03 | 只生成 1 个新批次；预算 8 万 vs 10 万冲突；旧回答保留；不新增预算问题 |
| 追加 M04 | 范围问题去重合并，问题数仍为 2，证据数增加 |
| 结论 | 27 项检查全部通过 |

## 6. 限制

- 按字符数而非真实 token 计数；不同模型 tokenizer 不同，字符上限是保守近似。
- 测试使用 `FakeProvider`，真实 Qwen 未联调；失败/超时为注入。
- 批次串行处理，未实现并行批次；取消只在批次边界生效。
- 冲突只记录并保留旧值，未实现人工裁定 UI；`resolution` 为空。
- 追加资料只分析新增部分，不会重算旧批次；若旧资料本身变化，需要新建 run。
- 回答保存在内存对象；未接 SQLite/前端持久化。
- 本次未推送 GitHub，仓库仍为 v0.3.0。
