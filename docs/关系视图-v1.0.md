## 1. 节点与边

节点：客户、项目、沟通、文件、需求、风险、待办、证据。

| 边类型 | 含义 | 是否需人工确认 |
|---|---|---|
| `direct_evidence` | 实体字段或证据 locator 直接指向 | 否 |
| `semantic_similar` | 名称相同或文本相似，仅作建议 | 是 |
| `manual_confirmed` | 人工建立的关联 | 否（已确认） |

每条边包含：`from`、`to`、`relation`、`type`、`why`、`evidence`、`sources`、`confidence`、`requires_confirmation`、`created_at`。

## 2. “为什么关联”说明

| 关系 | 说明模板 |
|---|---|
| 客户→项目 | 项目的 `customer_id` 指向客户，属于直接归属 |
| 项目→沟通 | 沟通的 `project_id` 指向项目，来源：导入归属 |
| 沟通→文件 | 沟通引用文件，属于直接来源 |
| 项目→需求 | 需求的 `project_id` 指向项目，来源：需求抽取 |
| 需求→证据 | 需求显式引用证据 ID |
| 证据→文件/沟通 | locator 指向来源对象 |
| 风险/待办→证据 | 显式引用来源证据 |
| 同名客户/项目 | “名称完全相同，疑似重复；仅作建议，不合并，需人工确认” |
| 相似需求 | “文本相似度 0.56（共同片段…）；仅作建议，不合并，需人工确认” |
| 人工关联 | “人工确认：操作人、时间、备注” |

## 3. 验证场景

### 3.1 同名客户

- 两个客户都叫“同名客户（虚构）”，保留为 `customer:c1` / `customer:c2`；
- 没有直接边；
- 只有一条 `semantic_similar` 建议边，`requires_confirmation=true`，说明“名称完全相同…不合并”。

### 3.2 同名项目

- 两个项目都叫“同名项目”，分属 c1/c2；
- 保留 `project:p1` / `project:p2`；
- 只有语义建议边，不合并；
- 需求 r1 只连 p1，需求 r3 只连 p2，没有 p1→r3。

### 3.3 跨客户相似需求

- r1（c1/p1）“设备台账要支持扫码查看档案”；
- r3（c2/p2）“设备台账需要扫码查看档案”；
- 文本相似度 0.56，生成 `semantic_similar` 边；
- `requires_confirmation=true`，不合并、不改变各自项目归属。

### 3.4 同一文件涉及多个项目

- 文件 `f1` 同时被 m1（p1）与 m2（p3）引用；
- 生成两条直接边 `m1→f1`、`m2→f1`；
- 文件节点 `project_ids=[p1,p3]`，不强行归到单一项目；
- 证据 ev1/ev2/ev4 都指向 f1，各自保留 locator。

### 3.5 人工确认

- 人工建立 `customer:c1 → file:f1` 的 `uses_file` 关联；
- 边类型 `manual_confirmed`，`requires_confirmation=false`；
- `why` 包含操作人“王工（我）”、时间、备注“合同由青岚提供”。

## 5. 限制

- 同名判断只做名称完全归一，不做工商主体/地址消歧。
- 相似度是中文二元组 Jaccard，阈值为 0.55；同义改写可能低于阈值。
- 语义边只作建议，不合并实体、不改变归属；必须人工确认后才可建立正式关系。
- 人工关联来自 `manual_links` 输入，当前无关系编辑 UI。
- 文件多项目归属由引用沟通推导，不修改文件本身的项目字段。
- 图目前输出 JSON，未做可视化画布；可直接用前端图库渲染。
- 本次未推送 GitHub，仓库仍为 v0.2.0。
