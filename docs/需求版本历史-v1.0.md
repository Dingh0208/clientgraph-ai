# 需求版本历史 v1.0

> 日期：2026-11-06
> 状态：追加式版本实现并完成三次沟通增量验证
> 代码：`requirement_history/`、`scripts/verify_requirement_history.py`
> 证据：`evidence/requirement-history-2026-11-06.json`

## 1. 原则

- **追加，不覆盖**：新资料只能新增版本，不能改写旧版本；
- 每条需求保留首次出现、修改、确认、取消的完整历史；
- 每个版本都带来源、发生时间、记录时间、变更原因和当时状态；
- 范围、预算、工期、验收标准变化时，项目版本记录前后值与证据；
- 新资料没提到的字段沿用上一版，不因“没提”而被清空。

## 2. 版本结构

```json
{
  "version": 3,
  "occurred_at": "2026-10-12T15:00:00+08:00",
  "recorded_at": "2026-11-06T…",
  "change_type": "modified | created | confirmed | cancelled",
  "status": "pending | confirmed | cancelled",
  "title": "上线时间",
  "description": "上线时间调整为 2026-12-01",
  "owner": null,
  "deadline": {
    "value": "2026-12-01",
    "status": "explicit",
    "raw": "2026-12-01"
  },
  "change_reason": "需求描述更新；截止时间由 2026-11-15 改为 2026-12-01",
  "changes": [
    {"field": "deadline", "before": {}, "after": {}, "evidence": []}
  ],
  "sources": []
}
```

项目版本另有 `scope`、`budget`、`acceptance` 与对应 `changes`。

## 3. 状态与事件

| 证据文本 | 处理 |
|---|---|
| 首次出现 | v1，`change_type=created`，状态 `pending` |
| `已确认 / 客户确认 / 确认范围` | 新版本，`change_type=confirmed`，状态 `confirmed` |
| `取消 / 不做 / 不进入一期 / 砍掉` | 新版本，`change_type=cancelled`，状态 `cancelled` |
| 字段变化 | `change_type=modified`，记录 `changes` |
| 仅重复提及、无变化 | 不新增版本，记入 `observations` |
| 后续资料不再提及 | 不自动取消，保留当前状态 |

## 4. 变化判定

| 层级 | 字段 | 比较 |
|---|---|---|
| 项目 | scope | 需求 key 集合的增删 |
| 项目 | budget | 状态与金额集合 |
| 项目 | deadline | 上线时间需求的值/状态/原文 |
| 项目 | acceptance | 验收标准文本列表 |
| 需求 | description | 归一化文本 |
| 需求 | owner | 负责人 |
| 需求 | deadline | 值/状态/原文 |
| 需求 | status | 待确认/已确认/已取消 |

项目预算在某一批缺失时沿用上一版；新资料只有明确给出新预算才变更。

- 每个版本都有来源文件、发生时间、变更原因和状态。

## 6. 限制

- 批次由调用方按沟通/会议/报价划分；当前没有自动会话切分。
- 需求匹配依赖抽取的 `canonical_key`；关键词表外的同义需求可能被当作新需求。
- 预算与验收标准是项目级；需求版本只携带工期、负责人、描述与状态。
- 确认/取消依赖文本关键词；“待确认”不会被误判为已确认。
- 新资料未提及的字段沿用上一版，不会自动清空或取消。
- 项目范围是累计并集，已取消需求仍保留在历史范围中。
- `recorded_at` 为本次运行时间，不是资料时间；`occurred_at` 才是沟通时间。
- 原型无版本回滚 UI；回滚需新增显式操作，不能直接改旧版本。
