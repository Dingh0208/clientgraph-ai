## 3. 规则

- 同一 `(项目, 维度, 需求作用域)` 下出现两个及以上不同归一值 → 冲突；
- A/B 按来源时间排序取前两个不同值；第三个及以后进入 `all_values`，`extra_value_count` 标记；
- 同一值重复出现不产生冲突；
- 每个冲突标记 `status=must_confirm`；
- `resolution/selected_value/model_choice` 一律为 null，`auto_resolved=false`，`write_blocked=true`；
- 检测器只读输入，不修改旧值；冲突是独立记录，等待人工确认；
- 关联：客户、项目、需求（若有）、待办（按需求或项目关联）。

## 4. 验证结果

18 条观测 → 8 个冲突，覆盖全部 8 个维度：

| 冲突 | 维度 | 值 A | 值 B | 关联 |
|---|---|---|---|---|
| K1 | 预算 | 预算 8 万 | 报价 100,000 元 | 项目 + T1/T2/T3 |
| K2 | 工期 | 2026-11-15 上线 | 2026-12-01 | R1 + T1 |
| K3 | 范围 | 一期包含审批流 | 审批流不进入一期 | R2 |
| K4 | 负责人 | 陈经理 | 王工 | R3 + T2 |
| K5 | 平台 | 微信小程序 | App | 项目 + T1/T2/T3 |
| K6 | 接口 | OA 单点登录 | ERP | 项目 + T1/T2/T3 |
| K7 | 权限 | 按车间隔离 | 全部可见 | R4 |
| K8 | 验收 | 118 台可扫码 | 120 台可扫码 | 项目 + T1/T2/T3 |

- 预算出现 3 个值（80,000 / 90,000 / 100,000），A/B + 1 个额外值；
- 同一负责人重复两次 → 0 冲突；
- 所有冲突 `must_confirm`，`resolution/model_choice` 为 null；
- 输入观测在检测前后完全一致（无静默覆盖）；
- 每个冲突都有双方来源与时间。

## 5. 限制

- 归一化基于规则：平台/接口只覆盖常见关键词，未覆盖全部厂商与私有系统。
- 权限与验收按文本完全归一比较，同义改写可能不识别为冲突。
- 范围只覆盖“审批/统计看板”等关键词对象；复杂范围需人工观测。
- A/B 只展示前两个不同值，第三个及以后在 `all_values`，不是逐对冲突。
- 检测器不做裁定、不合并、不写回；必须由人工确认后再更新业务记录。
- 未实现冲突解决 UI、冲突关闭与审计回写；当前只输出冲突记录。
- `observations_from_evidence` 是尽力而为的自动观测，复杂表述建议由抽取层提供结构化观测。
