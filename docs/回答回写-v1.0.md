# 回答回写需求/项目 v1.0

> 日期：2026-11-08
> 状态：目标选择、变更预览、人工确认、保存快照已实现并验证（64 项检查通过）
> 代码：`writeback/converter.py`、`scripts/verify_writeback.py`
> 证据：`evidence/answer-writeback-2026-11-08.json`

## 1. 流程

```
选择目标客户 / 项目 / 需求
        ↓
生成预览（只列回答明确支持的字段 + 证据）
        ↓
人工确认（确认人 + 预览令牌 + 目标指纹校验）
        ↓
保存：新需求 / 新版本 / 项目字段更新 + 操作快照
```

预览阶段不写任何数据：`writes=false`。没有确认人、预览被改动、目标在预览后被别人改过，都会拒绝保存。

## 2. 目标选择

必须先给 `customer_id` 与 `project_id`，模块不做自动猜测：

| 情况 | 错误码 |
|---|---|
| 未选客户或项目 | `E_TARGET_REQUIRED` |
| 客户不存在 | `E_CUSTOMER_NOT_FOUND` |
| 项目不存在 | `E_PROJECT_NOT_FOUND` |
| 项目不属于所选客户 | `E_TARGET_MISMATCH` |
| 需求不存在或不属于所选项目 | `E_REQUIREMENT_NOT_FOUND` / `E_TARGET_MISMATCH` |

`kind=requirement` 且带 `requirement_id` 表示更新需求；不带表示在所选项目下新建需求；`kind=project` 表示更新项目。

## 3. 只预填回答明确支持的字段

### 3.1 需求

| 字段 | 预填条件 | 说明 |
|---|---|---|
| 标题 | 仅新建 | “问题字段名：结构化值/回答摘要”，如“上线日期：2026-12-15” |
| 描述 | 新建必填；更新需回答 ≥6 字且含需求动词 | 更新时回答不像需求描述则不覆盖原描述 |
| 截止时间 | 仅完整年月日 | “月底/下周/尽快”等模糊表达不预填 |
| 负责人 | 出现“由 X 负责”或“负责人：X” | 否则保持原值 |
| 状态 | **永不预填** | 新建固定“待确认”，更新保持原状态 |

### 3.2 项目

| 字段 | 预填条件 |
|---|---|
| 预算 | 出现“预算/报价/费用”等 + 明确金额 |
| 工期 | 仅完整年月日 |
| 平台 | 识别到微信小程序 / App / H5 / 钉钉 / 企业微信 |
| 本期包含 | 明确“包含/要做/需要/上线”且不是“不包含” |
| 本期不包含 | 明确“不包含/不做/排除/砍掉” |

未识别、模糊或与当前值相同的字段不进入预览；与当前值相同的变更会被丢弃。预览同时给出 `skipped` 列表和原因，便于解释“为什么这个字段没变”。

## 4. 新需求默认待确认

新建需求固定：

- `status = 待确认`
- `review_state = pending`
- `confirmed_at = null`（人工确认的是“回写操作”，不等于需求已确认）
- `origin = clarification`
- `source_question_id`、`source_answer_id`、`source_excerpt`、`evidence` 全部落库

## 5. 需求 P0/P1/P2 独立判断

优先级不继承澄清问题的 `must_confirm / important / later`，由需求自身规则判断：

| 档位 | 判定信号 | 含义 |
|---|---|---|
| P2 | 二期、以后、后续、优化、可选、不急、暂不、最好 | 可延后 |
| P0 | 上线前、必须、合同、合规、安全、阻塞、验收必需、不能少、红线 | 缺失会阻塞交付 |
| P1 | 以上都没有 | 正常一期需求 |

判定顺序：先看延后信号（P2），再看硬约束（P0），其余 P1。预览输出 `suggested_priority`，并记录 `question_priority_ignored`，方便核对“问题优先级没有被拿来当需求优先级”。

## 6. 人工确认与防误写

保存必须同时满足：

1. `confirm=true`，否则 `E_CONFIRM_REQUIRED`；
2. 有确认人，否则 `E_CONFIRMER_REQUIRED`；
3. 预览令牌一致（`sha256` 摘要），否则 `E_PREVIEW_CHANGED`；
4. 预览内容未被改动，否则 `E_PREVIEW_TAMPERED`；
5. 目标记录指纹与预览时一致，否则 `E_TARGET_CHANGED`（防止预览后别人改了需求/项目）；
6. 同一预览只能保存一次，否则 `E_ALREADY_APPLIED`。

## 7. 保存快照

每次保存写一条操作记录 `operations[]`：

| 字段 | 说明 |
|---|---|
| `id` / `preview_id` | 操作编号与来源预览 |
| `action` | create_requirement / update_requirement / update_project |
| `target_before` / `target_after` | 保存前后完整快照（新建时 before 为 null） |
| `changes` | 每个字段的 before / after / supported_by / evidence |
| `question_id` / `answer_id` / `answer_text` / `answer_at` | 来源问答 |
| `evidence` | 回答证据 |
| `priority` | 新建需求时的 P0/P1/P2 与依据 |
| `confirmed_by` / `confirmed_at` | 人工确认痕迹 |
| `applied` | 是否已落库 |

需求额外追加 `versions[]`：新建写版本 1；更新写 `current_version + 1`，`content_json` 为该版本完整快照，旧版本永不修改。

## 8. 验证结果

| 场景 | 结果 |
|---|---|
| 未选目标 / 客户项目不匹配 / 需求不存在 | 分别拒绝，错误码明确 |
| 新建需求预览 | 标题、描述、截止时间、负责人 4 项；状态未进字段；固定待确认 |
| 模糊时间 | 不预填截止时间，`skipped` 说明原因 |
| 更新需求 | 仅描述、截止时间、负责人；状态、优先级、标题不变 |
| 无变化回答 | `fields` 为空 |
| 更新项目 | 预算、工期、本期不包含；平台与本期包含因未变化而不出现 |
| 未确认保存 | 拒绝，存储零写入 |
| 确认人为空 / 预览被改 / 令牌不符 / 目标已变 | 分别拒绝 |
| 重复提交同一预览 | 拒绝 |
| 新建保存 | 需求 R2、待确认、P1、版本 1、操作快照 before=null |
| 更新保存 | 版本 2，旧版本内容不变，未涉及字段保持原值 |
| 项目保存 | 快照隔离，之后改项目不影响已存快照 |
| 优先级独立性 | 问题 must_confirm → 需求 P2；问题 later → 需求 P0 |

检查项共 64 项，全部通过。

## 9. 限制

- 未接前端：目标选择、预览、确认按钮尚未落到原型页面；
- 字段识别为规则匹配，复杂句式（如一个回答同时改多个项目）需要人工在预览中判断，当前不支持逐字段手工改预览；
- 一次回写只作用于一个目标，跨客户/跨项目不合并；
- 没有撤销操作，只保留 before/after 快照与版本；
- 项目字段只覆盖预算、工期、平台、范围、负责人，项目阶段等字段未自动回填；
- 需求优先级为关键词规则，未结合历史报价与工作量；
- 未推送 GitHub，仓库仍为 v0.3.0。

## 10. 复现

```bash
python scripts/verify_writeback.py
```

最小用法：

```python
from writeback import build_preview, apply_preview

preview = build_preview(
    answer,                                    # 问题状态模块产出的回答
    {"kind": "requirement", "customer_id": "c1",
     "project_id": "p1", "requirement_id": "R1"},
    {"customers": customers, "projects": projects, "requirements": requirements},
)
# 界面展示 preview["fields"]、preview["skipped"]、preview["suggested_priority"]
result = apply_preview(preview, store, confirmed_by="老板", confirm=True,
                       token=preview["token"])
```
